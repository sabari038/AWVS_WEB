## Scan Execution Model

1. Frontend POSTs scan config to `/api/scans/start`
2. Backend generates scanId, stores `status: 'running'` in memoryStore
3. `child_process.spawn()` launches scanner with sanitized target IP
4. Scanner stdout lines are appended to `memoryStore.scans[scanId].logs[]`
5. Frontend polls `GET /api/scans/:id/status` every 2 seconds
6. On scanner exit, JSON output is read, parsed, stored
7. Risk Engine + FP Engine process the parsed data
8. Frontend receives `status: 'complete'` and navigates to dashboard

# 03 — FALSE POSITIVE ENGINE (NEW — KEY DIFFERENTIATOR)

> The FP Engine is what separates VulnScan Pro from simple scanners. It uses a multi-signal confidence scoring system to automatically detect likely false positives and surface them for analyst review — reducing alert fatigue by up to 60%.

## What Is a False Positive in Vulnerability Scanning?

A false positive occurs when the scanner reports a vulnerability that does not actually exist or is not exploitable in the target environment. Common causes:
- Version string mismatches (banner shows old version, software is patched)
- Patched vulnerabilities with unchanged version numbers
- Services behind firewalls the scanner cannot distinguish
- CVEs that apply to different OS editions
- Misidentified service banners

## FP Engine Architecture

```
CVE Finding (raw from scanner)
         │
         ▼
┌────────────────────────────────────────────┐
│        FP SIGNAL ANALYSIS (7 signals)      │
├────────────────────────────────────────────┤
│ Signal 1: Version String Confidence   0-25 │
│ Signal 2: Port Reachability Check     0-20 │
│ Signal 3: CVE-OS Platform Match       0-15 │
│ Signal 4: Service Banner Accuracy     0-15 │
│ Signal 5: Historical Patch Correlat.  0-10 │
│ Signal 6: Network Segment Exposure    0-10 │
│ Signal 7: CVSS Exploitability Vector  0-5  │
├────────────────────────────────────────────┤
│ TOTAL FP CONFIDENCE SCORE:          0-100  │
└────────────────┬───────────────────────────┘
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
    0-30%      31-69%    70-100%
 TRUE POSITIVE  REVIEW  FALSE POSITIVE
 (confirmed)  (analyst) (auto-flagged)
```

## FP Signal Definitions

| Signal | Max Score | How It Works | FP Indicator |
|---|---|---|---|
| Version String Confidence | 25 | Exact version extracted vs. banner guess | Fuzzy match → high FP risk |
| Port Reachability | 20 | Was the port actually open and responding? | Inferred only → FP risk |
| CVE-OS Platform Match | 15 | Does the CVE apply to the exact OS build? | Wrong edition → FP |
| Service Banner Accuracy | 15 | Did banner match expected service string? | Mismatch → FP risk |
| Patch Correlation | 10 | Cross-reference KB patch with installed updates | KB present → likely FP |
| Network Segment Exposure | 10 | Is port reachable from attacker path? | Firewalled → lower risk |
| CVSS Exploitability | 5 | Attack Vector: Network vs Local vs Physical | Local-only → lower true+ rate |

## FP Decision Logic (Pseudocode)

```javascript
function computeFPScore(finding) {
  let score = 0;

  // Signal 1: Version confidence
  if (finding.versionMatch === 'exact')    score += 0;   // Confirmed real
  if (finding.versionMatch === 'partial')  score += 15;  // Moderate FP risk
  if (finding.versionMatch === 'banner')   score += 25;  // High FP risk

  // Signal 2: Port actually open?
  if (!finding.portConfirmed)              score += 20;

  // Signal 3: OS platform match
  if (!finding.osPlatformMatch)            score += 15;

  // Signal 4: Banner accuracy
  if (finding.bannerMismatch)              score += 15;

  // Signal 5: Patch installed?
  if (finding.patchKBPresent)              score += 10;

  // Signal 6: Not network-reachable
  if (finding.behindFirewall)              score += 10;

  // Signal 7: Local exploitability only
  if (finding.attackVector === 'LOCAL')    score += 5;

  return {
    score,
    decision: score >= 70 ? 'false_positive'
            : score >= 31 ? 'needs_review'
            : 'confirmed_true_positive',
    confidence: `${score}%`
  };
}
```

# 05 — RISK SCORING LOGIC

## Asset Risk Score Formula

```
AssetRiskScore = (
  (avgCVSS × 0.40)           // Base CVSS contribution
+ (portExposureScore × 0.25) // Dangerous open ports
+ (serviceCriticality × 0.20)// Criticality of services
+ (internetFacing × 0.10)    // 1 if internet-exposed, 0 if LAN
+ (privilegeRequired × 0.05) // Lower priv req = higher score
) × fpAdjustmentFactor        // Reduces score after FP suppression

fpAdjustmentFactor = 1 - (confirmedFPs / totalFindings × 0.3)
Score range: 0–100
  Critical: 80–100
  High:     60–79
  Medium:   40–59
  Low:       0–39
```

## Port Exposure Scoring

| Port | Service | Score | Reason |
|---|---|---|---|
| 22 | SSH | +20 | Remote access, brute-force target |
| 3389 | RDP | +25 | Critical Windows remote desktop |
| 445 | SMB | +25 | WannaCry / EternalBlue vector |
| 80/443 | HTTP/S | +10 | Web attack surface |
| 1433 | MSSQL | +20 | Database exposure |
| 23 | Telnet | +30 | Unencrypted legacy protocol |
| Other | Unknown | +5 | Unknown service risk |

## Network Risk Score Formula

```
NetworkRiskScore = (
  max(AssetRiskScores) × 0.40   // Worst asset dominates
+ avg(AssetRiskScores) × 0.30   // Average spread
+ (criticalCount × 5) × 0.20   // Count of critical assets
+ (lateralMoveRisk) × 0.10      // Edges between critical nodes
)
```

## Risk Heat Map
Displayed on Dashboard as a grid table. Rows = Assets, Columns = Vulnerability Categories. Cell color follows severity system. Green stripe = FP suppressed cell.

## scanController.js
- `POST /api/scans/start` → validate, create scanId, spawn scanner process
- `GET /api/scans/:id/status` → return `{ status, progress, logsCount }`
- `GET /api/scans/:id/logs` → return logs array for live view
- `GET /api/scans/` → list all scans in memory
- `DELETE /api/scans/:id` → kill child process, mark `status: 'cancelled'`

## fpController.js ← NEW
- `GET /api/fp/` → return all FP analysis results for current scan
- `GET /api/fp/:cveId` → detailed FP signal breakdown for one CVE
- `POST /api/fp/:cveId/decide` → analyst submits `{ decision, reason }`
- `POST /api/fp/:cveId/override` → override auto-FP, mark as real finding
- `GET /api/fp/report` → FP audit trail for export
- `GET /api/fp/stats` → `{ autoFP, needsReview, confirmed, overridden }`

## fpEngine.js ← NEW (Core FP Service)
- `analyzeFinding(finding)` → runs all 7 signals, returns score + decision
- `computeVersionSignal(finding)` → exact/partial/banner match check
- `computePortSignal(finding)` → cross-checks port open state
- `computePlatformSignal(finding)` → CVE CPE vs. detected OS match
- `computeBannerSignal(finding)` → banner string analysis
- `computePatchSignal(finding)` → KB lookup in Windows update list
- `computeNetworkSignal(finding)` → firewall/segment analysis
- `computeExploitabilitySignal(finding)` → CVSS AV vector check
- `batchAnalyze(findings[])` → processes all findings, stores in `memoryStore.fpDecisions`

## riskEngine.js
- `computeAssetRisk(asset, vulns, fpDecisions)` → returns 0–100 score
- `computeNetworkRisk(assets)` → returns network-level risk
- `generateHeatMap(assets, categories)` → returns 2D grid data
- `recomputeAfterFPUpdate(scanId)` → recalculates all scores after any FP change

## scannerService.js — Safe Execution Rules
- Sanitize all inputs: IP validated with regex **before** passing to child process
- Use `spawn()` not `exec()` — avoids shell injection
- Set timeout: kill process after configurable `maxDuration`
- Stream stdout lines → append to `memoryStore.scans[id].logs`
- On close: read `tmp/scan_output.json`, pass to `jsonParser.js`
- **Never** pass raw user input as shell arguments

## topologyService.js
- `parseTopology(scanOutput)` → extract nodes and edges from scanner JSON
- `enrichWithRiskScores(topology, riskData)` → add risk metadata to nodes
- `enrichWithFPData(topology, fpDecisions)` → mark FP-suppressed nodes
- `generateGraphLayout(topology)` → return D3-compatible force graph data
